# Аккаунты, счета и подключение УТ 11.5

Целевая база: 1С:Предприятие 8.3.27.1936, Управление торговлей 11.5.22.186.

## Что уже делает сайт

- `/register`, `/login`, `/account`: регистрация, вход, выход, личная история заказов.
- Заказ создаётся только в авторизованном аккаунте. Переданный клиентом userId не используется. Чужой заказ или счёт недоступен даже с его прежней персональной ссылкой.
- Пароли хранятся как scrypt-хеши с индивидуальной солью, сессии — как хеши случайных токенов. Cookie HttpOnly, SameSite=Lax, Secure на HTTPS, срок 7 дней. Выход отзывает сессию.
- `/account/invoice/<orderId>`: счёт по приложенному образцу, печать и сохранение в PDF через браузер. Данные поставщика взяты из образца, покупатель и товары — из заказа. Подпись и печать не копируются. До запуска бухгалтерия должна проверить банковские реквизиты.
- Рабочий счёт появляется после получения его номера, даты и НДС из 1С. Номер заказа сайта `AN-…` не подменяет номер счёта 1С. Demo-счета помечены «ОБРАЗЕЦ — НЕ ДЛЯ ОПЛАТЫ».
- `/admin`: последние заказы, журнал пакетов, загрузка JSON с названиями, ценами и остатками, ссылка на опубликованную рабочую 1С. Вход в саму 1С выполняется на её странице, сайт не собирает пароль 1С.

Почтовые подтверждения регистрации, восстановление пароля и отправка счетов по email пока не подключены. Указанный email не считается подтверждённым. Старые гостевые заказы не привязываются к аккаунтам по совпадению email: это позволило бы получить чужие данные.

## Хранение и запуск

Бесплатный Render подходит для демонстрации. Его локальная файловая система непостоянна: после пересоздания сервиса аккаунты и заказы могут пропасть. Для рабочих заказов нужен постоянный диск с резервным копированием. Текущая SQLite-конфигурация рассчитана на один экземпляр приложения. Переход на внешний PostgreSQL требует отдельной миграции.

Docker запускает `scripts/start-store.mjs`. По умолчанию остаётся demo, обмен отключён и реальные платежи невозможны. Для рабочего запуска задаются в настройках хостинга:

```
PAYMENT_MODE=live
ANADO_DB=/var/data/anado.sqlite
SITE_URL=https://soite.onrender.com
LIVE_PAYMENTS_ENABLED=0
```

`/var/data` — пример точки монтирования **реального постоянного диска**, доступного для записи пользователю `node` (UID 1000). Один лишь путь не делает диск постоянным. При первом запуске копируется публичный каталог; существующая БД не заменяется. Для переноса существующих аккаунтов используйте SQLite backup/VACUUM INTO при остановленных записях, а не копирование одного файла активной WAL-базы.

Добавьте секрет `ONE_C_TOKEN` (минимум 24 случайных символа, рекомендуется 32 случайных байта), сгенерированный локально, в секретные настройки Render и в защищённые настройки обработки 1С. Не включайте его в Git, скриншоты и журналы. Опционально задайте `ONE_C_WEB_URL` — HTTPS-адрес уже опубликованного веб-клиента 1С.

### Первый администратор без консоли (бесплатный Render)

1. В Render откройте сервис `soite` → **Environment** → **Add Environment Variable**.
2. Добавьте `ADMIN_SETUP_EMAIL` — ваш email, с которым будете входить на сайт.
3. Добавьте `ADMIN_SETUP_TOKEN` — сгенерированный менеджером паролей случайный ключ от 32 до 256 символов без пробелов. Ключ хранится только в настройках сервера; не отправляйте его в чат и не помещайте в URL.
4. Нажмите **Save, rebuild, and deploy** (или Save с последующим Deploy), дождитесь статуса **Live**.
5. Откройте `https://soite.onrender.com/admin/setup`. Войдите или зарегистрируйте аккаунт с email из `ADMIN_SETUP_EMAIL`. Если аккаунт пропал после пересоздания demo-сервиса, зарегистрируйте его снова.
6. На странице настройки укажите пароль этого аккаунта и ключ из `ADMIN_SETUP_TOKEN`, нажмите **Назначить администратором**. Откроется `/admin`.

Проверяются email владельца, пароль и ключ. Первый зарегистрировавшийся не получает права автоматически. Назначение выполняется атомарно; при существующем администраторе или записи о завершении повтор запрещён, в том числе после изменения ключа. Старые сессии владельца отзываются, браузер получает новую. Других администраторов через эту страницу добавить нельзя.

При постоянном хранилище после успешного назначения удалите обе `ADMIN_SETUP_*` переменные из Render; вход затем выполняется по обычным email и паролю аккаунта. На бесплатном Render изменение переменных может пересоздать сервис и стереть локальную базу вместе с аккаунтом и отметкой о завершении. Пока используете этот demo-вариант, оставьте переменные: настройка закрыта на время существования базы. Если база исчезнет, владелец сможет снова зарегистрироваться и пройти настройку. Для постоянного доступа и настоящих заказов нужно постоянное хранилище.

### Если после входа открывается личный кабинет

Откройте `/admin` напрямую: вход с этой страницы сохраняет назначение и возвращает в админку. У администратора в `/account` есть ссылка **Администрирование**. Если email текущего аккаунта совпадает с `ADMIN_SETUP_EMAIL` и настройка ещё не завершена, показывается **Настроить администратора**.

Переменные Render сами по себе не выдают роль: её нужно назначить на `/admin/setup` с паролем аккаунта и ключом. Теперь `/admin` показывает текущий email и понятное сообщение, если прав нет, вместо 404. При другом email на странице настройки есть кнопка смены аккаунта. Если переменные отсутствуют, ключ короче 32 символов или содержит пробел/перенос строки, страница сообщает причину без вывода значений секретов.

### Назначение через консоль сервера

Если доступна Shell/SSH, после регистрации владельца выполните с той же `ANADO_DB`:

```
node scripts/promote-admin.mjs ваш-email
```

Это выдаёт права существующему аккаунту. Обычный клиент без ключа владельца не может назначить себе администратора. Не используйте тестовые пароли для владельца. Резервируйте SQLite штатным backup-механизмом; храните копии с ограниченным доступом.

## Подключение 1С

**Готова серверная сторона обмена. Установленного расширения/обработки в вашей базе ещё нет.** Файл `integrations/1c/HttpTransport.bsl` — исходник HTTP-транспорта для разработчика 1С, не устанавливаемый `.epf` и не готовый документ обмена. В рабочей 1С он не запускался. Нельзя обещать автоматическую синхронизацию до установки и проверки адаптера в копии базы.

Для адаптера нужно выбрать вашу организацию, склад, вид цены, соглашение и правило создания контрагентов. Затем:

1. Получить `GET /api/integrations/1c/inventory?offset=0` и следующие страницы `nextOffset`. Сопоставить `sourceOfferId` сайта с номенклатурой и характеристикой 1С; это разные идентификаторы. Проверять неоднозначные артикулы вручную.
2. Регламентным заданием отправлять актуальные названия, цены, остатки и налоговые реквизиты через `POST /api/integrations/1c/inventory`. Пример пакета ниже. Тот же JSON можно загрузить вручную в `/admin`. Полную `.dt`/`.1cd` базу на сайт загружать не нужно: она не принимается.
3. Получать `GET /api/integrations/1c/orders` (до 100 новых live-заказов). В 1С сохранять уникальный ID сайта в регистре соответствий с уникальностью. В одной транзакции создавать документ заказа и соответствие; повтор запроса должен возвращать существующий документ, а не создавать дубль.
4. Создать счёт в 1С по заказу, используя штатную нумерацию базы. Сохранять соответствие отдельно для заказа и счёта. Проверить сумму: цены единиц на сайте округлены до рублей **до умножения**. Цена/количество в счёте должны совпадать со снимком заказа, а не с уже изменившимся прайсом.
5. Передать счёт через `POST /api/integrations/1c/invoices` (пример ниже). Только после успешной передачи счёта подтвердить импорт заказа через `POST /api/integrations/1c/orders` с GUID документа заказа. Так сбой передачи счёта не потеряется после удаления заказа из очереди. Оба запроса можно повторять.
6. Повторять обмен по расписанию (например, каждые 5 минут). При сетевой ошибке хранить задания и повторять с задержкой, не создавать новый batchId для повторной отправки того же пакета. Не журналировать Authorization или персональные данные целиком.

Сайт сохраняет подтверждённый GUID заказа 1С. Попытка подтвердить тот же заказ с другим GUID возвращает 409. Рабочие счета неизменяемы после регистрации: другой номер/сумма/НДС требуют согласованного сценария корректировки, который здесь не реализован. Статусы отгрузки, банковской оплаты счёта, отмены и возвраты автоматически из 1С пока не передаются. Статус оплаты картой меняет только проверенный ответ ЮKassa.

## Пакет каталога

Все API 1С требуют `Authorization: Bearer <секрет>` и HTTPS. POST — `Content-Type: application/json`. Размер пакета каталога до 512 000 байт; делите большую выгрузку на части с отдельными batchId.

```json
{
  "batchId": "ut11-20261025-0001",
  "offers": [{
    "id": "идентификатор-варианта-сайта",
    "name": "Название комплектации из 1С",
    "productName": "Название карточки товара",
    "priceKopecks": 12907067,
    "stock": 5,
    "vatCode": 1,
    "paymentSubject": "commodity"
  }]
}
```

`name` и `productName` необязательны; без них название сохраняется. Обновляются существующие сопоставленные позиции, поиск переиндексируется. Неизвестный ID отклоняет пакет целиком. Создание новых карточек, фото и категорий этим API не выполняется. Налоговый код 1 в примере не является рекомендацией: ставку/предмет расчёта берут из действительных данных учёта. `priceKopecks` — целые копейки, отображение и заказ округляются до целого рубля. Нельзя просто отправить цену в рублях в это поле.

## Счёт из 1С

```json
{
  "orderId": "AN-20261025-ABCDEF123456",
  "documentId": "GUID-счёта-1С",
  "number": "26-2293",
  "issuedAt": "2026-10-25",
  "totalKopecks": 25814200,
  "taxes": [{"label": "Без НДС", "amountKopecks": 0}]
}
```

`taxes` содержит ровно одну запись для каждой строки `items` заказа, в том же порядке. Сумма НДС указывается для всей строки, не единицы. Сайт не угадывает налоговый режим. `totalKopecks` должен строго совпасть с суммой сохранённого заказа. Для позиций «цена по запросу» счёт не выписывается до согласования; изменение цены уже созданного заказа этим API не предусмотрено. Номер выше — пример; номер из присланного шаблона не переиспользуется.

Подтверждение импорта заказа:

```json
{"orderId":"AN-20261025-ABCDEF123456","documentId":"GUID-заказа-1С"}
```

## Приёмка перед рабочим запуском

В копии базы и отдельном тестовом сервисе: повторный импорт одного заказа даёт один документ; повтор счёта не меняет номер; чужой аккаунт не видит счёт; неправильная сумма/неизвестный товар отклоняются; отключение сети между шагами не теряет заказ; перезапуск сайта сохраняет аккаунты. Проверить НДС, округление, реквизиты поставщика, несколько строк, физлицо/ИП/ООО и печать.

Сайт проверен локальными тестами. Настоящая 1С, доступ к банку, реальное списание и рабочие документы в ходе разработки не использовались. Онлайн-оплату оставляйте выключенной до настройки резервов, фискализации и проверки специалистом 1С.
