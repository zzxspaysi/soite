# ЮKassa и 1С:Управление торговлей

## Текущий режим

`PAYMENT_MODE=demo` по умолчанию. Оплата явно обозначена как демонстрационная, банковские данные не запрашиваются, средства не списываются, заказы остаются в локальной базе. Маркер `demo_paid` никогда не становится `paid` и не выгружается в 1С.

## ЮKassa

Серверный адаптер: `lib/commerce.mjs`. Поддерживаются `bank_card` и `sbp` с переходом на размещённую у провайдера страницу. Сервер рассчитывает сумму по своим данным, отправляет email и позиции для чека, использует номер заказа как `Idempotence-Key`. Цена из тела браузерного запроса игнорируется.

Переменные production-хостинга:

| Переменная               | Назначение                                                                                                                                             |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `PAYMENT_MODE`           | `demo` или `live`; включать live после завершения подключения                                                                                          |
| `LIVE_PAYMENTS_ENABLED`  | По умолчанию `0`. Значение `1` разрешает создание реальных онлайн-платежей; устанавливать только после завершения резервирования и приёмочных проверок |
| `SITE_URL`               | Публичный HTTPS-адрес без завершающего слеша                                                                                                           |
| `YOOKASSA_SHOP_ID`       | Идентификатор магазина                                                                                                                                 |
| `YOOKASSA_SECRET_KEY`    | Секретный ключ через секрет-хранилище хостинга                                                                                                         |
| `YOOKASSA_AUTHORIZATION` | Альтернатива предыдущей паре: полный заголовок `Basic …`; удобно для proxy-backed secret в облачной среде                                              |
| `ONE_C_TOKEN`            | Отдельный локальный серверный секрет длиной минимум 24 символа для входящего обмена с 1С                                                               |
| `ANADO_DB`               | Путь к базе на постоянном диске                                                                                                                        |

Секретные значения не добавлять в Git, логи и переписку. Для облачного прокси `YOOKASSA_AUTHORIZATION` передаётся без локального перекодирования; секрет разрешается только для `api.yookassa.ru`. Для входящего `ONE_C_TOKEN` нужен настоящий секрет в процессе сервера через защищённое хранилище хостинга: proxy-подстановка исходящего HTTP его не заменяет.

Уведомления в кабинете ЮKassa:

```
POST https://<ваш-домен>/api/payments/yookassa/webhook
```

События `payment.succeeded`, `payment.canceled`. Тело уведомления не считается подтверждением платежа: для известного локального live-платежа сервер получает платёж повторным авторизованным GET из API ЮKassa и сверяет ID, metadata заказа, сумму, RUB, `test=false`, `paid=true` и статус. Неизвестные ID игнорируются без обращения к провайдеру. Повторные события безопасны. Возврат на страницу заказа не меняет статус на «оплачен». Проверка статуса на странице запрашивает данные провайдера с отдельным ограничением частоты.

Для реальной оплаты нужны свежие (не старше 24 часов) сведения из 1С: цена, достаточный остаток, `vatCode` и `paymentSubject` каждой позиции. Налоговый код и предмет расчёта нельзя угадывать: услуги/лицензии/оборудование могут иметь разные значения. Допустимые значения должны соответствовать договору и текущей документации ЮKassa. Фискальные настройки, система налогообложения, чеки при предоплате и окончательном расчёте требуют проверки с бухгалтерией и выбранной онлайн-кассой.

Тесты платёжного адаптера используют локальные mock-ответы. Проверка настоящего тестового магазина ЮKassa и реальное списание в этой работе не выполнялись. Для отдельной проверки sandbox-магазина понадобится согласовать режим `test=true`: текущий live-обработчик намеренно не засчитывает тестовые платежи как реальные.

## Обмен с 1С:УТ

Подготовлен **HTTP JSON-контракт**, а не готовое штатное расширение CommerceML. На стороне вашей конкретной версии 1С нужно написать/настроить регламентное задание или внешнюю обработку. Все запросы — только по HTTPS, с заголовком `Authorization: Bearer <ONE_C_TOKEN>`. Без настроенного секрета API возвращает 401.

1. Получить сопоставление вариантов исходного каталога:

```
GET /api/integrations/1c/inventory?offset=0
```

Ответ: `offers` (до 500), `total`, `nextOffset`. `sourceOfferId` — исходный ID ANADO; `sku` — исходный артикул; `productId` — стабильный ID карточки. Это **не GUID 1С**. Сохраните таблицу соответствия GUID номенклатуры/характеристики ↔ sourceOfferId; автоматическое совпадение по названию не выполняется.

2. Передать актуальные цены, остатки и реквизиты чека:

```json
{
  "batchId": "unique-batch-id-from-1c",
  "offers": [
    {
      "id": "12118",
      "priceKopecks": 2600000,
      "stock": 5,
      "vatCode": 1,
      "paymentSubject": "commodity"
    }
  ]
}
```

```
POST /api/integrations/1c/inventory
```

Пример `vatCode=1` — только пример, не рекомендация вашей налоговой ставки. Цена — целые копейки, остаток — целое неотрицательное число. Сервер проверяет весь пакет перед транзакцией. Повторный `batchId` не применяется ещё раз; неизвестный вариант отклоняет пакет целиком. Время получения ставит сервер. Если налоговые поля не переданы, онлайн-оплата такого варианта блокируется.

Цены на витрине округляются до ближайшего целого рубля: от 50 копеек вверх. Округление применяется к цене единицы до умножения на количество и используется одинаково в каталоге, корзине, серверном расчёте, заказе и платёжном чеке (`lib/money.mjs`). Исходная цена из 1С хранится в целых копейках без изменений; например, 129 070,67 ₽ отображается и заказывается как 129 071 ₽, две единицы — 258 142 ₽.

3. Забрать новые заказы:

```
GET /api/integrations/1c/orders
```

Только live-заказы без подтверждённого импорта, до 100 за запрос. Содержат `customer`, `items`, `totalKopecks`, `paymentMethod`, `status`. Создавайте документ по уникальному `id` сайта: повторное получение не должно создавать второй документ. Demo-заказы исключены.

4. Подтвердить запись документа:

```json
{ "orderId": "AN-YYYYMMDD-XXXXXX", "documentId": "GUID-документа-1С" }
```

```
POST /api/integrations/1c/orders
```

Подтверждение убирает заказ из списка новых. Оно не меняет платёжный статус и не является подтверждением оплаты. Номер документа пока используется как обязательное подтверждение со стороны клиента 1С; отдельный журнал GUID и последующая синхронизация отгрузки ещё не реализованы.

## Что доделать при подключении конкретной базы

- Версия/конфигурация 1С:УТ, организации, склады, вид цены, соглашения и характеристики номенклатуры.
- Резервирование товаров в 1С и синхронизация резервов до реального списания. Текущая проверка остатка не создаёт резерв: конкурентные покупки одного последнего товара требуют завершения этого сценария до включения live.
- Изменение/отмена заказа, отгрузка, возвраты платежей и освобождение резервов; повторная передача изменений уже выгруженных заказов.
- Фискализация с реальными налоговыми реквизитами и проверка доставки/окончательного расчёта.
- Реквизиты и договор-оферта продавца, окончательная политика обработки данных, email/SMS-уведомления, мониторинг, ограничение доступа к интеграции на хостинге и резервные копии.

До этих настроек оставляйте `PAYMENT_MODE=demo`. Тестовое оформление и разработку витрины можно выполнять полностью без ключей.

## Доступ к заказам и ограничения API

Новые ссылки имеют вид `/order/<id>#token=<секрет>`: фрагмент после `#` не передаётся HTTP-серверу. Браузер читает его и запрашивает `GET /api/orders/<id>` с заголовком `Authorization: Bearer <секрет>`. API больше не принимает ключ в query string. Старые ссылки на страницу с `?token=…` браузер преобразует в новый вид; их первоначальный запрос всё ещё мог попасть в журналы сервера, поэтому такие журналы требуют ограничения доступа. Персональная ссылка даёт доступ к заказу — не публикуйте её. Ответы API заказов имеют `Cache-Control: no-store`, сайт использует `Referrer-Policy: no-referrer`.

JSON-запросы ограничены по размеру и времени чтения: 64 000 байт обычно, 16 000 для webhook, 512 000 для пакета остатков 1С. Большую выгрузку остатков делите на пакеты с разными `batchId`. Лимиты частоты включают общий бюджет, который не зависит от подменяемого клиентом IP-заголовка. Это защита одного процесса; для нескольких экземпляров и защиты от распределённой нагрузки нужен общий лимитер или правила на стороне хостинга.

Демонстрационная база очищает старые demo-заказы при создании новых, сохраняя около 500 последних. Live-заказы этой очисткой не затрагиваются. На бесплатном Render база также может исчезнуть при перезапуске сервиса: не используйте демо для хранения настоящих заказов.
